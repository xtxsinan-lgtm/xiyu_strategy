## 2. 体验支柱（每个机制都要回答"它服务哪根柱子"）

1. **万里粮道**：后勤是看得见、可规划、会出错的玩法，不是记账。
2. **将在外**：时间差与授权——诏令和情报都在路上走，玩家在不确定中预先授权。
3. **帝国对联盟**：汉与匈奴是两套不同的循环，换边就是另一个游戏。
4. **人与史**：每局都能讲出一个有名有姓、有史可对照的故事。

## 4. spec 必须包含的章节（模板）

每个 spec 文件按以下顺序组织，缺一章即视为未完成：

1. **目的与支柱**：服务哪根体验支柱；它让哪些回合决策更难做（L7）。
2. **玩家视角**：玩家在什么时候、在哪个界面、做什么决策；一个具体的回合示例（带数字）。
3. **状态变量**：表格列出 `名称 | 所属对象 | 类型 | 取值范围 | 初值 | JSON 键 | 存档字段`。
4. **规则与公式**：每条规则编号（如 `S03-R07`）；公式给出全部系数的默认值与可调范围；结算时机（每旬 / 每月 / 每季开头 / 季末 / 事件时）与先后顺序。
5. **命令**：玩家/AI 可下达的命令表 `命令 id | 参数 | 前置条件 | 消耗 | 效果 | 失败返回`。
6. **与其他系统的接口**：导出（别人可读）、导入（我读别人的）、接口需求（需要别人新增的）。
7. **AI 使用要点**：AI 需要什么信息来使用本系统（细节归 S08）。
8. **UI 需求**：需要展示什么、在哪里、tooltip 文案草稿（细节归 S07）。
9. **玩家可见文本**：所有字符串的中文草稿，带本地化 key（`ui.court.trust_label` 之类）。
10. **边界情况**：至少 10 条（人物死亡于途中、目标城被攻陷、存档在文书途中等）。
11. **调参旋钮与预期**：哪些参数最敏感，调高/调低会发生什么。
12. **验收测试**：可由 headless 测试或 Python 模拟验证的断言，写成 `Given / When / Then`。
13. **未决问题**：列出，并在 STATUS.md 登记。

**完成度标准（"可比拟商业游戏"的定义）**：一名没看过任何讨论的程序员只读 spec，就能实现该系统而无需再问设计问题；一名策划只读 spec，就能写出全部 UI 文本和平衡表。

## 5. 数值与命名约定

- **时间**：1 旬 = 10 天；1 月 = 3 旬；1 季 = 3 月 = 9 旬；年从正月开始。日期写作 `前119年3月上旬`。
- **单位**：粮以"斛"计；钱以"钱"（游戏内抽象单位，不对应五铢实数）计；兵以"人"计；马以"匹"计。
- **百分比**统一用 0–100 的整数存储；概率用 0.0–1.0 浮点。
- **JSON 键**：snake_case，按 spec 分段，例如 `balance.json → court.trust_initial`。新系统可新建 `data/court.json`、`data/tribes.json`、`data/events.json`、`data/characters.json`、`data/edicts.json`、`data/scenarios/*.json`。
- **ID**：节点 id 沿用 `scenario_mvp.json`；人物 id `han_zheng_ji`、`xn_xianxianshan`；事件 id `evt_white_disaster`；命令 id 动词开头 `distribute_rewards`。
- **随机数**：一律走 `GameState.rng`；spec 中涉及随机的地方写明分布。
- **节点标签**（替代 AI 硬编码）：`hexi_commandery`、`frontier_gate`、`staging_xn`、`ambush_road`、`citystate_north`、`citystate_south`、`great_power`、`xn_core` 等，由 S08 定稿、各 spec 引用。

## 6. 验证方法（S09）

不写游戏代码也能验证的部分，用 Python 完成：

1. **纸面模拟器**（`design_sim/`，纯 Python 3 标准库，可选 numpy）：在**季**粒度上抽象全部新规则（数值从 spec 的默认值表读入同一份 `design_sim/params.json`），对双方各实现 3–5 个机器人策略（贪心、激进、保守、随机、简单前瞻搜索）。
2. **校准**：先把**现有**规则以同样的抽象度移植，确认能复现现有 Godot 统计特征（汉主胜利≈0、到期计分多、分数收敛）。复现不了说明抽象有偏差，需修正后才能用于评估新设计。
3. **指标**：L12 验收数字；每回合"非劣选项数"（决策密度）；支配策略检测（某策略对所有对手胜率 > 70% 即视为支配）；逆转率；资源曲线；事件触发分布；一局时长。
4. **文字试玩**：模拟器提供文字界面（CLI），由 LLM agent 扮演玩家逐回合下令并写"试玩日志"（每回合：看到了什么、考虑了哪些选项、为什么选、是否觉得无聊/困惑），用来检查决策是否有趣、信息是否够用。用户本人也可以用同一 CLI 试玩。
5. **局限**：模拟验证的是数学与结构（可达性、多样性、支配策略、决策密度），**不能**验证手感、可读性和美术。这些留给垂直切片后的真人试玩。

```mermaid
flowchart LR
  W0["W0 圣经与模板"] --> W1["W1 系统 spec 初稿 S01–S05 + 现状模拟校准"]
```
